### Workflow

#### Pin Content
1. Client calls `/pin/<cid>` endpoint
2. Endpoint validates user owns file, queues pin_content_task, returns 202 + task_id
3. Celery worker receives task (state: STARTED)
4. Worker queries File by CID
5. On success: Updates pin_status to PINNED, updates TaskStatus (SUCCESS), creates AuditLog
6. On failure: Retries with backoff or logs to TaskStatus (FAILURE)

#### Unpin Content
1. Client calls `/unpin/<cid>` endpoint
2. Endpoint validates user owns file, queues unpin_content_task, returns 202 + task_id
3. Celery worker receives task (state: STARTED)
4. Worker queries File by CID
5. On success: Updates pin_status to UNPINNED, updates TaskStatus (SUCCESS), creates AuditLog
6. On failure: Retries with backoff or logs to TaskStatus (FAILURE)

### Error Handling
- File not found: Gracefully fail with FAILURE state (no retry)
- Database errors: Retry with exponential backoff (3 attempts)
- Other exceptions: Logged and stored in TaskStatus

### Database Updates
- File model: pin_status updated (PINNED or UNPINNED)
- TaskStatus model: Tracks task state and result
- AuditLog: Entry created with action="pin" or "unpin" and CID details

### Retry Policy
- Max retries: 3
- Base delay: 60 seconds
- Exponential backoff: 60s, 120s, 240s
- Jitter: Applied by Celery automatically
